Reproducer Flow Architecture

An agent team that takes one paper and its scope.txt, picks the claims to reproduce, implements and runs the experiments on a shared GPU, computes every result twice from the raw run files, and judges each claim against the paper's own numbers. This page describes the design as of the open-ended rewrite of 4 November 2026.

01Pipeline at a glance

Six phases. Work flows left to right; checks sit on the arrows. Each experiment builds in parallel with the others, but every GPU job waits in one shared queue that runs a single job at a time.

What the flow guarantees

  • Every claimed number is recomputed twice from raw run files, by two different models.
  • Every builder round is reviewed against the paper before the next one.
  • Every final verdict sits next to its rule verdict, so a judge override is visible.
  • Everything an agent did is journaled and replayable.

What it no longer enforces (by choice)

  • Blindness: builders may read the paper and its reported numbers.
  • A GPU-hour limit: gpu_hours is a planning hint only.
  • Procedure rules in prompts: no learning checks, seed rules or leak checks.

02Phases in detail

1 · Lead

One session, label lead, on the strong tier, with two turns.

  • Turn 1, claims. Lists the arms (every method or baseline) as slugs and extracts the claims the scope asks for. For a paper that proposes a method, its benchmark numbers come first, as value claims. Each claim is a value, an ordering (better arm vs worse arm, with paper_a/paper_b) or a predicate (~= or >= a target). It also records source (table, text or figure) and, for a figure, which panel and curve.
  • Checks after turn 1. Non-slug arm names and claim ids are renamed everywhere. A claim with a missing number, unknown arm or a paper number outside its metric's units is sent back; on the last of max_tries it is dropped and the usable claims go on.
  • Figure reads (section 05) replace numbers that only exist in a plot.
  • Turn 2, experiments. Picks what to reproduce within roughly gpu_hours, defers the rest with a reason, and groups the selected claims into experiments: arms, a short procedure pointing to the paper's sections, seeds, metric names with exact definitions, the metric each claim uses, and what a reviewer should check. Unknown claim ids and repeats are dropped and unaddressed claims deferred, then the structure is checked (arms exist, compared arms run, metrics defined).

2 · Build

One builder session per experiment, label builder:<experiment>, strong tier, all experiments in parallel. Each round is one builder turn followed by one fresh reviewer call (reviewer:<experiment>, cheap tier).

  1. Builder reads the paper, implements the experiment in repo/arms/<experiment>/, runs a short pilot on the GPU and reports stage pilot with its run files.
  2. Reviewer reads the paper, the code and the run files and returns issues, each marked blocking or not.
  3. Blocking issues go back to the builder at the same stage. A clean pilot review sends the builder on to the full runs (stage full); a clean full review ends the build.
  4. The loop stops after build_rounds builder turns (default 5). An open review caps the experiment at partial; full runs that never finished cap it at could_not_test.

3 · Evaluate

The evaluator (strong) writes its own code in repo/eval/ and computes every claim from the raw run files, as the paper defines the metric. It gets two tries to cover every claim. Then one audit:<claim> agent per claim (cheap, read-only shell) recomputes it independently with a python heredoc. If the two disagree by more than 2% on a value or an arm mean, the claim is capped at partial; a paired difference only counts when the auditor's agrees.

4 · Tune (optional, tune: true)

Claims whose blind result does not match the paper go to one tuner session (strong) that sees the paper's numbers and may change any setting, working in repo/tuned/<experiment>/. Each round it tries up to tune_trials settings, logs them to trials.json, writes the best setting's runs as run files and answers with its numbers. The flow compares them with the paper and feeds the gap back, for up to tune_rounds rounds, stopping early once every claim matches. The best tuned result then gets its own audit (audit:<claim>:tuned). The target is the method's own number: an ordering only counts as a tuned match if the method arm is within tolerance of paper_a.

5 · Judge

Pure-python rule verdicts per claim (section 06), with caps applied. Then the judge agent (cheap) reads the paper, the run files, the rows, the caps and the audits, and sets a final verdict with a reason for every claim. It may depart from a rule verdict but must cite a file or number; both verdicts are kept. If it gives no valid answer in max_tries, the rule verdicts stand and a cap says so.

6 · Report

The reporter writes report.md around the verdict table. The flow appends sections it writes itself, so their wording is exact: caps with their open findings, tuning changes per claim, and the paper numbers read off figures. The report states that builders could read the paper's numbers and that results were computed independently.

03Roles, models, access

Workers run on the strong tier and their checkers on the cheap tier, so a checker is never the same model as the worker it checks. Strong is deepseek/deepseek-v4.1-flash-1017, cheap is z-ai/glm-5.3-flash, both through OpenRouter at reasoning effort low, with a 1M-token context. 04Run-file contract

The one format the flow fixes, because two agents must compute every claim from it independently. Builders write it under repo/arms/, the tuner under repo/tuned/.

repo/arms/<experiment>/runs/<arm>/seed<k>.json
{
  "experiment": "fc-tanh-edgestability",
  "arm": "gd-lr-2over100",
  "seed": 0,
  "job_id": "5e6e1f6f-1a79-43c7-83e1-c29bdd22f7da",   // the gpurun job that produced it, or "local"
  "config": { every hyperparameter the run used },
  "metrics": { "late_sharpness_over_2overeta": 1.077, "breakeven_iteration": 900, ... },
  "curves": { "sharpness": [[0, 82.3], [10, 83.0], ...] }
}
A run that did not finish has no file.

Claims point to a metric name in the experiment's metrics list. The evaluator and auditor fill a fixed answer shape per claim: value for value and predicate claims, or a, b (mean with a 95% CI over seeds) and diff (paired a − b over shared seeds) for an ordering, plus the run files they used in sources.

05Reading numbers off figures

A PDF's text keeps a plot's tick labels but not its curves, so a number that only exists in a plot used to be guessed (RePPO's Breakout score came out as 0.8, 0.72 and 0.55 in three runs). Now any claim whose source is figure, or that cites a figure without a source, gets two independent readings before the lead writes its experiments.

Limits that keep readers on task

  • At most 6 view_page calls per turn (readers once zoomed 60+ times without answering).
  • 25 model calls per figure turn, with the wrap-up warning 15 calls before.
  • Guidance: one whole-page view, then crop to the panel once or twice.

Measured on RePPO Fig. 6a

  • Both models read RePPO m=1.2 at ~170 raw → 0.68 ± 0.045 normalized.
  • PPO-Q + Ent: ~95–100 raw → 0.39 ± 0.05.
  • 10 page views, $0.005 for both readings.

07Every hard-coded gate

What still stops, retries, repairs or caps automatically. Everything else is left to the agents and the reviewer.

Flow: structure

  • Arm names and claim ids must be slugs: renamed, not sent back.
  • Claim fields (value has a number, predicate has op and target, ordering has two listed arms): retried, dropped on the last try.
  • Unit check: a normalized, fraction, probability or proportion metric may not have a paper number above 1.5: retried.
  • Figure readings: outside the metric's range (a fraction that reads negative) → dropped; two readings that disagree → one tie-break read, then the outlier is dropped; the disagreement widens the tolerance only to 50%.
  • Selection: unknown ids and repeats dropped, unaddressed claims deferred, cut to max_claims.
  • Experiment: slug id, arms from the list, compared arms run, metrics defined: retried.
  • No usable claims, no valid experiments, or no experiment finished: run stops (could_not_test).

Flow: build answers

  • No run files reported, or a reported .json that is missing or does not parse: sent back (skipped when the flow cannot see the run root).
  • A builder's blocking questions: one lead confer turn answers them, at most max_questions (2) per experiment.
  • A review issue with owner: "spec": the same turn answers it and may patch acceptance, procedure, arms or open_choices; the round is not spent, up to max_spec_fixes (2).
  • An answer with source: "decision" is appended to open_choices (basis: "lead") and printed in the report.
  • A builder-owned blocking guess with a measured sensitivity_pct ≤ 5%: a note, not a blocker.
  • A limit the paper does not state that binds past 1% (10% when declared guard): owned by spec, so the lead decides — accept the narrowing (recorded) or raise it.
  • A run file reported outside the run root: sent back; the flow only counts what it can read.
  • The run stops before a verdict: report.md is still written, with every open finding.

Flow: results

  • Review open after the last round: cap partial.
  • Full runs never finished: cap could_not_test.
  • Evaluator vs audit more than 2% apart: cap partial; paired CI ignored unless the auditor's agrees.
  • Rule verdicts with the 15% tolerance; judge must give one verdict per claim (retried).
  • Smoke run: cap partial.

Agent loop

  • 5 invalid submits or bare replies end a turn (it is skipped).
  • 200 model calls per turn (80 reviewer, 60 audit and judge, 25 figure readers); wrap-up warning 15 before.
  • Answers validated against a JSON schema; extra fields dropped; broken brackets repaired only if the result validates.
  • 6 page views per turn.
  • USD limit per run (--usd), optional token limit.

Tools and GPU

  • Role access table (reads, writes, shell, GPU) enforced in tools.py.
  • Shell in bubblewrap, no network, empty environment, 1,800 s per command.
  • Uploads ≤ 500 MB; submit timeout 600 s + 10 s per MB.
  • Jobs that only inspect or install are refused.
  • 30 jobs per role per run; gpu_wait ≤ 1,800 s.
  • Agents see and cancel only their own run's jobs.

08The agent loop

Each agent is a tool-calling loop over the OpenRouter chat API (framework/agents.py). The model gets the role's tools plus submit; a turn ends when a submit validates.

Answers

  • submit.result is declared as a JSON object, so models do not hand-escape a 30 KB document into a string.
  • A string still parses, with raw newlines allowed; a bracket-rebalancing repair handles dropped item braces, stray closers and trailing commas.
  • A schema rejection lists up to 6 errors at once.
  • Every rejected submit is saved to runs/<id>/rejected/<label>.<n>.txt.

Sessions

  • Multi-turn roles are sessions whose turns are labelled base, base#2, …
  • A skipped turn leaves nothing in the session, so until one turn has answered, a retry carries the original request too.
  • Near 85% of the context window, old tool output is shrunk; paper reads stay whole.

Images

  • view_page renders with pdfium at 2×, crops, enlarges small crops to 1,200 px, encodes JPEG.
  • Images follow the step's tool results as one user message with image parts.
  • All pdfium calls share one lock: concurrent renders crashed whole runs with no traceback.

09Sandbox and GPU

Agents run on the laptop (WSL). Their shell is a bubblewrap sandbox with only their readable paths mounted (read-only, plus their writable directory), no network, no inherited environment, and a CPU Python with numpy, scipy, pandas, torch and jax for small checks.

GPU work goes through gpurun tools that the framework runs outside the sandbox, over ssh to the gpu_runner daemon on the GPU box (1× A100 40 GB per job). A submit tars one readable directory (no .git, .venv or caches), the daemon runs the commands in order inside it, and gpu_download copies results back into a writable directory. The GPU box has network and a shared uv cache, so jobs install from pyproject.toml and download data themselves.

The queue is the bottleneck. The daemon runs one job at a time across every run and every user. Three papers in parallel overlap their agent work, but their GPU jobs still go one after another.

GPU-hour ledger. Each run records when it first saw a job running and finished. Because the daemon reports no times, a job that ran while the laptop slept was charged the whole night (17 and 34 "GPU-hours"). The limit is therefore off (enforce_budget = false); the ledger is kept for information.

10Journal, resume, pause

Journal and resume

Every agent call is journaled in runs/<id>/journal.jsonl with a signature over its prompt, label, phase, model, schema and (for sessions) prior turns. --resume runs/<id> replays every call whose signature still matches, at no cost, and reruns from the first that does not. Editing a prompt therefore reruns everything after it; pure-python changes replay cleanly.

Stopping cleanly

On SIGTERM or SIGINT a run cancels its own GPU jobs before exiting, and it cancels leftovers on normal exit too. ./pause_runs.sh freezes every live run (SIGSTOP to its process group) for offline periods; ./unpause_runs.sh continues them. GPU jobs keep running meanwhile.

./launch.sh <paper> --usd 50                          # new run, detached, log in logs/
./launch.sh <paper> --resume runs/<id> --usd 50       # continue from the journal
./pause_runs.sh   /   ./unpause_runs.sh                # before and after going offline

13How it got here

Each step was a response to something a live run did.

  • 2 NovThirteen roles: reader, spec, expert, planner, contracts, contracts-check, builder, challenger, gate, audit, tuner, judge, reporter, with a job graph, arm families and a leak check on specs.
  • 2–3 NovGLM broke large spec answers it had to escape into a string: submit takes an object, brackets are repaired, rejected answers are saved.
  • 3 NovChecks repair instead of reject (renames, selection repair); GPU job cap raised to 30; upload timeout scales with size; tolerance raised from 5% to 15%.
  • 3 NovA RePPO run whose arms played randomly passed every review: tuning now targets the method's own number, and the lead puts benchmark numbers first.
  • 3 NovSimplified to lead → builder ↔ reviewer → evaluator + audit → tuner → judge. Planner, contracts, expert, protocol risks and the leak check removed.
  • 3 NovFigure reading with two models and view_page; unit check on paper numbers; raw-unit uncertainties converted.
  • 4 NovGPU-hour limit off after a sleeping laptop charged a night of phantom time.
  • 4 NovOpen-ended prompts: every role may read the paper; learning, seed and procedure rules removed; pdfium lock after concurrent renders crashed two runs.

14Known gaps

RePPO's Q-critic arms

In the last build, every arm with a Q critic stayed at random level, including plain PPO-Q, while the V-critic arms learned. That builder bootstrapped the Q critic's λ-return with max over actions, marked "assumed"; the one implementation that learned used the on-policy Q(s′, a′). The current run tests whether builders that can read Algorithm 1 get it right.

One GPU queue

Parallel papers wait on each other's jobs. A second runner or per-run queues would cut wall time more than any flow change.

GPU-hour ledger

Wrong after any sleep or pause. A real fix needs job start and end times from gpu_runner.

Network on the GPU box

Jobs can clone any repository. Builders so far took only official baselines and recorded their source; a hard block needs bubblewrap on the GPU box and a setup-only network phase.

Laptop orchestration

Runs live on the laptop. Pausing before going offline works; moving orchestration to an always-on machine would remove the problem.

Not blind

Builders can see target numbers. The safeguard is the independent recompute from run files that carry their GPU job id, not ignorance of the target.
